= Rejected Idea: Character Class Pre-filtering via bytes.IndexAny
:sectnums:

== Summary

A proposal was investigated to accelerate patterns starting with character classes (e.g., `\w`, `[a-z]`) by using `bytes.IndexAny` as a pre-filter, similar to how the `0-Pass` strategy uses `bytes.Index` for literal prefixes. However, simulations proved that the current DFA execution loop is already faster than `bytes.IndexAny` for most common character sets.

== Investigation Goal

The goal was to achieve $O(n/m)$-like skip performance for non-literal patterns by leveraging SIMD-accelerated scanning provided by the Go standard library's `bytes.IndexAny`.

== Simulation Results

The following benchmarks were conducted on an `amd64` (Go 1.25.1) environment, simulating a 1MB buffer scan where the match is located at the very end.

|===
| Strategy | Throughput (MB/s) | Note

| `bytes.Index` (Literal Skip)
| ~25,000 MB/s
| Existing "0-Pass" strategy (SIMD)

| **DFA Execution Loop**
| **~2,400 MB/s**
| **Current Pure DFA implementation**

| BP-DFA Loop
| ~1,300 MB/s
| Current Bit-Parallel implementation

| `bytes.IndexAny` (`\w`)
| ~1,200 MB/s
| Proposed Pre-filter for `[0-9A-Za-z_]`

| `bytes.IndexAny` (Unicode Leads)
| ~115 MB/s
| Proposed Pre-filter for `0x80-0xFF`
|===

== Analysis of Failure

The proposal was rejected, and later **strictly prohibited** in all hot loops (including SearchWarp), for the following technical reasons:

1. **DFA & SWAR Efficiency**: The current DFA loop runs at 2.4 GB/s, and our custom SWAR kernels run at 2.7-3.3 GB/s. `bytes.IndexAny` bottlenecks at ~1.2 GB/s, making it a performance degrader rather than an optimizer.
2. **`bytes.IndexAny` Overhead**: Unlike `bytes.Index`, `bytes.IndexAny` in Go 1.25.1 still incurs significant overhead from UTF-8 decoding and generic bitset lookups.
3. **High False Positive Rate**: Characters in common classes like `\w` appear frequently. A pre-filter that hits every few characters adds overhead before entering the DFA.

== 2026 Update: Full Prohibition

In May 2026, the engine's "Search Strategy Dispatch" was updated to completely eliminate `bytes.IndexAny`. Even for SearchWarp (Discovery Phase), the engine now mandates project-specific SWAR kernels (`ir.IndexClass`).

|===
| Strategy | Throughput (MB/s) | Result

| `bytes.Index` (Literal) | ~25,000 | **Keep**
| **SWAR (SingleRange)** | **~2,700** | **Preferred**
| Pure DFA Loop | ~2,400 | **Base**
| `bytes.IndexAny` (`\w`) | **~1,200** | **Strictly Prohibited**
|===

== Conclusion

Standard library `bytes.IndexAny` is formally banned from the `go-regexp-re` hot paths. All character set searches must use `ir.IndexClass` (SWAR).
